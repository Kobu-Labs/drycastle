# Engine comparison for the shooter PoC (issue #2)

Research date: 2026-11-10. Question: compare Godot 4, Unity, Unreal 5 and Bevy for the Suchohrad project (Linux+Windows clients, headless Linux dedicated server, built-in multiplayer for a 16-64 player shooter, importing a procedurally generated glTF map, low-poly open-world performance, licence/cost, vehicle physics, learning curve for a senior backend dev with no engine experience).

Confidence legend: **[P]** = read directly on the owning project's official docs/repo this session. **[S]** = secondary (forum/blog/search summary) - treat as a lead, not a fact. **[?]** = not verified; open question.

## Per-engine findings

### Godot 4
- Current stable line is 4.7.x (4.7.2 released 2026-08-18) [P: https://godotengine.org/download/archive/]. MIT licence, no fees, only a copyright/licence notice in the shipped game [P: https://godotengine.org/license/].
- Dedicated server: since 4.0 any Godot binary runs with `--headless` (headless display server + dummy audio); the "Export as dedicated server" mode adds the `dedicated_server` feature tag and can strip textures/materials/meshes to placeholders. Audio cannot be stripped automatically yet; "Remove" mode breaks scenes that reference removed files [P: https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_dedicated_servers.html]. The docs also describe a systemd service for Linux hosting.
- Networking: `MultiplayerPeer` implementations ENet, WebSocket, WebRTC; the high-level API uses UDP only; RPCs via `@rpc` with reliable/unreliable channels; the page itself states no maturity level, and tells you to treat all client input as untrusted and do server-authoritative logic [P: https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html]. Sample code is not built for dedicated servers; you must restructure startup.
- Interest management exists: `MultiplayerSynchronizer` visibility filters (per peer) and spawners that spawn/despawn based on visibility [P: https://docs.godotengine.org/en/stable/classes/class_multiplayersynchronizer.html]. Limits: no Object/Resource properties; RIDs/instance IDs do not sync.
- **Maturity evidence**: issue #103938, still open when read, shows a hard cap of 64 watched properties per synchronizer with silent failure outside the editor (seen on 4.4 RCs, so recheck on 4.7) [P: https://github.com/godotengine/godot/issues/103938]. There is no client-side prediction, lag compensation or rollback in the documented API; you would write these yourself [inference from the docs read; not an explicit statement]. Claims like "fine for 2-16 players, bottlenecks at 32+" and "ENet only handles 32 players" came from blogs/forums and are **unverified** [S: https://forum.godotengine.org/t/can-godot-netcode-scale-for-large-multiplayer-scenarios/83561]. No official 64-player benchmark exists that I could find. Verdict: adequate for a hobby 16-32 player shooter with custom netcode work; MMO scale is unproven.
- glTF: runtime loading is supported through `GLTFDocument`/`GLTFState` in exported projects; binary .glb preferred; docs warn it is not meant for project-owned files (use normal import) [P: https://docs.godotengine.org/en/stable/tutorials/io/runtime_file_loading_and_saving.html]. For a pipeline, importing the generated glTF at editor time with an import script (for colliders/navmesh from node names/extras) is the usual route [?: the using_gltf page returned 404; verify against current docs].
- Navigation: the docs I read show building navmeshes procedurally and passing them to `NavigationServer3D`; I could not confirm a runtime bake-from-geometry workflow from that page [?].
- Vehicles: `VehicleBody3D` is a raycast vehicle with documented limitations; Jolt became an alternative in 4.4 and is the default for new projects, though its thread-safety mode is "experimental" and some joint features are missing [P: https://docs.godotengine.org/en/stable/classes/class_vehiclebody3d.html, https://docs.godotengine.org/en/stable/tutorials/physics/using_jolt_physics.html]. Whether `VehicleBody3D` works with Jolt was not stated; check.
- Rendering: occlusion culling (CPU, Embree) helps indoor scenes mostly; HLOD (visibility ranges), mesh LOD and MultiMesh exist but the page gives no setup details [P: https://docs.godotengine.org/en/stable/tutorials/3d/occlusion_culling.html]. Open-world streaming of parcels is something you would build yourself [inference].

### Unity 6
- Cost: Personal free up to $200k revenue+funding; Pro $2,310/seat/yr in 2026 with a 5% increase from 2026-01-12; the runtime fee was cancelled 2024-09-12 [P: https://unity.com/products/pricing-updates]. Terms are a vendor contract that has changed before (2023 runtime-fee episode); that is a trust consideration, not a technical one [judgement].
- Dedicated Server build target exists for Linux/macOS/Windows and strips unneeded assets/code [P: https://docs.unity.com/en-us/engine/6000.0/manual/platform-specific/dedicated-server/introduction]. Linux setup details not on that page.
- Netcode for GameObjects supports Win/mac/Linux/mobile; the page I read did not cover server-authority or dedicated servers, and its version info was inconsistent [P: https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.0/manual/index.html]. I did not verify scale for 64 players, NGO vs Entities netcode, or Unity's own multiplayer-service dependencies [?].
- glTF: glTFast 6.0.1 for editor and runtime import, claims full glTF 2.0 and Draco/KTX/meshopt [P: https://docs.unity3d.com/Packages/com.unity.cloud.gltfast@6.0/manual/index.html]. Licence of the package not stated on that page.
- Not verified: vehicle physics, performance tooling, navmesh, learning curve beyond "C# is familiar to a backend dev" (judgement).

### Unreal Engine 5
- Dedicated server requires a **source build** and a **C++ project** [P: https://dev.epicgames.com/documentation/en-us/unreal-engine/setting-up-dedicated-servers-in-unreal-engine]. That page is Windows-only in its steps and does not mention Linux. Linux cross-compile from Windows is supported with an Epic toolchain (v26/clang-20.1.8 for UE 5.7-5.8) [P: https://dev.epicgames.com/documentation/en-us/unreal-engine/linux-development-requirements-for-unreal-engine]. For a Linux dev machine, native Linux builds exist (Setup.sh downloads a toolchain) [P, same page]. Source builds mean long compiles and large disk use [judgement].
- Networking is the deepest of the four: server-authoritative, property replication, RepNotify, RPCs, relevancy/priority/dormancy, Replication Graph for many actors, Iris as the newest system [P: https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-overview-for-unreal-engine].
- Licence: 5% royalty on gross revenue after the first $1M per product, with a quarterly $10k exclusion and a 3.5% rate under an Epic Games Store programme [S: web search summary of Epic pages and EULA; the Epic licence/FAQ/EULA URLs returned 403 to me, so confirm in the EULA]. For a hobby project this is likely moot.
- Not verified (doc pages fetched were empty): glTF import path, Chaos Vehicles status. Learning curve is the steepest (C++ + large editor) [judgement].

### Bevy 0.20
- Dual MIT/Apache-2.0. The project states it is early-stage, "important features are missing", breaking API changes about every three months, and its own intro recommends Godot as "much more feature-complete and stable" [P: https://github.com/bevyengine/bevy, https://bevy.org/learn/quick-start/introduction/].
- No engine networking. bevy_replicon 0.45 (targets Bevy 0.20.0; no I/O; transports via separate crates such as renet/quinnet; some ecosystem crates unmaintained) [P: https://github.com/simgine/bevy_replicon]. lightyear 0.31 (Bevy 0.20; prediction, interpolation, bandwidth caps, UDP/WebSocket/Steam; book is WIP; two cited games, one a game-jam entry) [P: https://github.com/cBournhonesque/lightyear]. Both are third-party with their own release cadence, which compounds Bevy's breakage.
- glTF via `bevy_gltf` 0.20.1: no Draco, meshopt, quantization or GPU-instancing extensions; texture-transform limited [P: https://docs.rs/bevy_gltf/latest/bevy_gltf/]. A custom pipeline could avoid these extensions.
- Not verified: editor (neither page mentions one; my belief is there is none, unconfirmed), vehicle physics, Avian (docs site unreachable).
- Fit: strongest for a backend dev who likes Rust/ECS and wants a lean server; weakest for a solo dev with no 3D experience who needs an editor, tooling and a finished physics/vehicle story.

## Recommendation (for the map #1 decision; the human decides)
1. **Godot 4 is the best fit for the stated constraints**: MIT, lightweight Linux headless export, built-in multiplayer with interest management, glTF support, small editor suited to a first-time 3D dev, and low-poly is well within its renderer. Risks: networking is less proven at 32-64 players (and no built-in prediction/lag compensation), vehicles are weak out of the box, and open-world streaming is DIY.
2. **Unity 6** is the safest fallback if Godot netcode or vehicles fail the PoC: C# fits a backend dev, glTFast and a Dedicated Server target exist. Cost is fine for a hobby, but vendor-licence risk and heavier tooling.
3. **Unreal** is the most capable server/replication stack but needs a C++ source build, steep learning, and is overkill for low-poly; not recommended for a solo first-engine project.
4. **Bevy** is not recommended for the PoC given immaturity, quarterly breakage, no editor, and third-party networking.

## Suggested spike (cheap, decisive)
Before committing, build a 1-day Godot headless server with 64 scripted clients moving and shooting; measure CPU, bandwidth per player and tick stability, and check the 64-property cap on 4.7. Load one generated glTF street at runtime and in-editor. Try a VehicleBody3D under Jolt.
