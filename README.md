# Suchohrad Game

A GTA-like open-world game set in the real village of Suchohrad (Slovakia), in a simplified low-poly style. The base map is generated by a re-runnable, fully scripted pipeline from open data, with no manual map building. Mods (for example the shooter PoC) are separate games built on that base map.

## Repo layout

| Path | What it is |
| --- | --- |
| `pipeline/` | Python (uv) project that generates the base map. Package `suchohrad_pipeline`, one stub per stage. |
| `pipeline/config/` | Rules, manual building overrides and hand edits (`edits.json`) for the pipeline. |
| `godot/MapLoader/` | C# class library, shared runtime loader for chunk glTF and parcel replacement. |
| `godot/netspike/` | Godot C# project, 64-client headless netcode spike (issue #18); report in `docs/spikes/netcode-spike.md`. |
| `godot/viewer/` | Godot 4.7 C# project for looking at the generated map. |
| `mods/shooter/` | Shooter PoC (stub). Design notes are in `mods/shooter.md`. |
| `docs/` | Agent docs, ADRs (`docs/adr/`). `GLOSSARY.md` defines the domain terms. |
| `exerpt.md` | Original project brief. |

## Pinned versions

- Godot 4.7.2 mono (also in `.godot-version`)
- .NET 8 (SDK 8.0)
- Python 3.13 (`pipeline/.python-version`; `uv` installs it if missing)

## Setup

Requires `uv`, `make`, the .NET 8 SDK and Godot 4.7.2 mono on your `PATH` as `godot`.

```sh
make setup    # uv sync in pipeline/
make test     # pytest
make lint     # ruff check
```

## Running

```sh
make map        # run every pipeline stage in order (fetch ... export)
make fetch      # run only the fetch stage (downloads raw data into data/raw/)
make normalise  # raw data -> local metres in data/work/normalised/
make parcels    # parcel registry, kinds, building assignment; prints a report
make rules      # building heights, roofs, colours -> data/work/buildings.json
make terrain    # DMR 5.0 -> height grid, ground flattened under buildings (data/work/terrain*)
make roads      # OSM highways -> road graph (data/work/roads.json)
make props      # fences, trees, spawn candidates (data/work/props.json, spawns.json)
make export     # chunk glTFs, parcels.json, roads.json, spawns.json, manifest.json -> out/map/
make preview    # out/preview/topdown.png, iso.png, iso_close.png (matplotlib; EXAG=3 relief factor)
make map AREA=village   # the same for the whole village (any target takes AREA=slice|village)
make viewer         # build and run the Godot viewer (see "Viewer" below)
make viewer-smoke   # headless smoke test of the viewer and the loader
make viewer-edit-smoke  # hot reload end to end (scratch export, headless viewer, edits written during the run)
make viewer-shot    # windowed run, writes PNGs to out/screens/
make netspike-quick # netcode spike, N=8, 15 s (needs a map: MAP=/path/to/out/map)
make netspike       # netcode spike, N=16/32/64, 60 s per variant (about 30 minutes)
```

To build the C# projects without the editor:

```sh
dotnet build godot/MapLoader/MapLoader.csproj
dotnet build godot/viewer/viewer.csproj
```

## Configuring the slice and fetching data

The map is built for a small slice of the village first. The slice is a square around the
centroid of one OSM way (for example a building), set in a local, gitignored file:

```sh
cp pipeline/config/slice.example.yaml pipeline/config/slice.local.yaml
# edit osm_way (OSM way id), radius_m (default 100) and margin_m (extra metres fetched, default 25)
make fetch
```

`make fetch` writes to `data/raw/` (gitignored): `osm.json` (Overpass: buildings, highways,
barriers, landuse, natural tree/wood/water), `parcels.geojson` (INSPIRE cadastral parcels
intersecting the box, WFS) and `dmr5.tif` (DMR 5.0 terrain, 1 m, EPSG:3046, via INSPIRE WCS).
Each file has a `<name>.meta.json` sidecar (request, url, fetched-at, sha256, source, licence,
attribution) and `manifest.json` lists the sources, licences and required attribution.

Reruns skip files whose request parameters are unchanged and download nothing; use
`cd pipeline && uv run python -m suchohrad_pipeline fetch --force` to refetch everything.
Requests are sequential, use the User-Agent `suchohrad-pipeline`, have timeouts and retry with
backoff (Overpass falls back to a second public instance).

## Whole village (areas)

The pipeline runs over two areas around the same centre, chosen with `AREA=slice` (default) or
`AREA=village` for make, or `--area` on the CLI:

| | slice | village |
| --- | --- | --- |
| size | `radius_m` (default 100) | `village.radius_m` (default 700, `village.margin_m` defaults to `margin_m`) |
| raw data | `data/raw/` | `data/village/raw/` |
| work files | `data/work/` | `data/village/work/` |
| export, previews | `out/map/`, `out/preview/` | `out/village/map/`, `out/village/preview/` |
| `map_version` | `0.2.0-slice` | `0.2.0-village` |

Add the `village:` section to `pipeline/config/slice.local.yaml` (see `slice.example.yaml`).
Both areas share the one committed registry `registry/parcels.registry.json`. Fetching the
village is polite: Overpass in one request, cadastral WFS paged (`startIndex`, 5000 per page, sorted)
when a page is full, the DMR raster in WCS tiles of at most 1000 m per side (cached per tile in
`dmr_tiles/`) that are mosaicked into `dmr5.tif`. All are cached; `--force` refetches.

`rules.yaml` has an `areas.<name>` overlay that is merged over a section only for that area. The
village profile uses fewer fences without collision boxes, fewer trees (`props.trees.max_per_chunk`
caps rule-based trees per chunk) and more spawn candidates, to keep chunk files small for 16-64
players on weak GPUs. `make preview AREA=village` also writes `overview.png`: the parcels and
buildings with the 250 m chunk grid and chunk indices.

Village numbers (one real run, default settings): 1165 parcels, 384 buildings, 40 chunk files,
about 400k visual and 75k collision triangles in total, at most about 24k visual triangles and 1.7 MB
per chunk, 29 MB of glb in all (fences without collision and the tree cap took that from 39 MB). A
full run after the fetch takes about half a minute; the fetch takes about two minutes. Nothing was
measured in Godot yet; terrain (4 m grid, 7.7k triangles per chunk) is now the biggest visual part.

## Normalise and the parcel registry

`make normalise` reprojects the OSM data and cadastral parcels from WGS84 to EPSG:5514 and then
shifts them into a local metric frame whose origin is the slice centre (`slice_centre.json`).
Axes stay those of EPSG:5514. It writes `data/work/normalised/{buildings,highways,landuse,parcels}.geojson`
(local metres, gitignored) and `data/work/frame.json`.

`make parcels` gives every cadastral parcel an own stable ID (`P-0001`, 4 digits, growing when
needed) and writes `data/work/parcels.json` (ID, cadastral reference, polygon, area, kind,
anchor point, building ids, 250 m chunk index) and prints a report (counts by kind, buildings
assigned or unassigned, new and retired IDs). Kind and building-assignment rules, with their
order and thresholds, are documented in `pipeline/config/rules.yaml`.

The committed registry `registry/parcels.registry.json` is the source of truth for IDs. Per
parcel it holds `id`, `cadastral_ref`, `previous_refs`, `status` (`active` or `retired`) and a
geometry signature in absolute EPSG:5514 metres (area, centroid and outline, used for matching;
it comes from the cadastre only). Each regeneration matches current parcels to it:

1. same cadastral reference keeps the ID;
2. otherwise an unmatched registry entry with outline IoU >= 0.5 keeps its ID (the parcel was
   renumbered; the old reference is appended to `previous_refs`);
3. otherwise the parcel is new and gets the next ID after the highest ever used, in cadastral
   reference order;
4. entries nobody claimed become `retired`. They are never deleted and their IDs never reused.

To regenerate after the cadastre or OSM changed: `make fetch` (or `fetch --force`), `make parcels`
(which needs `make normalise` first), then review and commit the `registry/` diff. Re-running
on unchanged input leaves the registry byte-identical. A run only retires entries whose outline
lies inside the box it fetched (`fetched_bounds_epsg5514` in `frame.json`); entries outside are
left untouched. So the village after the slice keeps every ID and numbers the new parcels after the
highest one, and the slice after the village retires nothing. Shrinking or moving an area retires
only what is inside the new box and no longer in the cadastre (reversible: an entry whose exact
reference reappears is revived). Retiring or
reassigning IDs is a breaking change of the map artifact (see the versioning decision).

## Buildings: rules, meshes, export

`make rules` writes `data/work/buildings.json`, one entry per building assigned to a parcel
(buildings without a parcel are skipped and counted): ID, parcel ID, footprint (local metres,
holes allowed), `height_m` (to the roof top), `eave_height_m`, `roof_height_m`, `levels`, `roof`
(`flat`, `gabled`, `hipped`), `ridge_dir` (radians, pitched roofs only), `wall_colour` and
`roof_colour` (RGB). Precedence: `pipeline/config/overrides.yaml` > OSM tags (`height`,
`building:levels`, `roof:shape`, `roof:levels`) > building-type class > footprint-area class.
Thresholds, classes and colour palettes are in the `buildings` section of
`pipeline/config/rules.yaml`. A gabled or hipped ridge runs along the longest side of the
minimum rotated rectangle; if the footprint fills less than 80% of it the roof is flat. Colours
and the small random choices are drawn from a generator seeded with sha256 of
`<parcel id>:<building id>`, so reruns give identical output. The override file format (by parcel
ID or OSM id, any building field) is documented at the top of `overrides.yaml`.

## Terrain, roads, props, spawns

Settings for all of this are in the `terrain`, `roads`, `props` and `spawns` sections of
`pipeline/config/rules.yaml`.

**Terrain** (`make terrain`): `data/raw/dmr5.tif` (EPSG:3046) is resampled bilinearly into a
regular height grid in the local frame (default step about 4 m; chunk borders are grid lines, so
neighbouring chunks share border vertices). Terrain is meshed only where the DMR raster covers
all four corners of a grid cell; nothing is clamped or invented outside it, and chunks without
covered cells get no terrain. Heights are metres above the DMR datum, not rebased. The ground under
each building footprint (grown by a margin) is flattened to the footprint's mean elevation and
blends back to the natural height over a few metres; the building stands at that elevation.
Buildings outside coverage (their chunk files have no terrain) take the clamped height of the grid
edge; road ribbons, fences, trees and spawns outside coverage are dropped.

**Roads** (`make roads`): highways from `normalised/highways.geojson` (classes and widths in
`rules.yaml`; an OSM `width` or `lanes` tag wins) become graph nodes and edges in
`out/map/roads.json` (`nodes`: id, x, y; `edges`: id, osm_id, from, to, polyline, highway, width,
oneway, surface, length_m; local metres, x east, y north). Ribbon meshes are draped on the
terrain surface and lifted by `lift_m` (0.05 m); overlapping ribbons at intersections are
accepted in v1, and a higher road class sits a hair above a lower one.

**Props** (`make props`): low fences (thin boxes, 1.2 m) along the boundaries of building plots
and of gardens near buildings (seeded per parcel, a gate gap on road frontage, no fence through
buildings or the carriageway), OSM trees and seeded rule-based trees in gardens, plots and forests
(blocky box canopy, or stacked pyramids in forests). Fences also get a simple closed-box
collision node; trees have no collision in v1.

**Hand edits** (`pipeline/config/edits.json`, read by the props stage; `--edits PATH` overrides the
file): per-parcel fence mode (`auto`, `none`, `custom` with a type, height, colour and gaps),
property groups (`G-NNNN`: one fence around the members' combined outer edge), tree density or
count with a seed offset, and placed objects (`pack:` or `prim:` assets, absolute S-JTSK metres).
Objects go to `work/objects.json`. The format and validator are documented in
`pipeline/src/suchohrad_pipeline/edits.py`. Entries for parcels that no longer exist are skipped
with a warning; schema errors fail the stage.

**Spawns**: `out/map/spawns.json` has a seeded subset (default 60) of points on roads and on
garden, field and other parcels, at least `min_building_distance_m` from any building, with
elevation, parcel, highway type (roads) and chunk index.

## Export

`make export` writes `out/map/` (gitignored): `chunks/chunk_<ix>_<iy>.glb` (one glTF per 250 m
chunk that has buildings or terrain; Y-up axes x east, y up, z -north, metres, one frame for all
chunks). Nodes per chunk glb: `parcel_<ID>_visual` (walls and roof, flat per-face vertex colours)
and `parcel_<ID>_collision` (extruded footprint, no roof detail) for each parcel with buildings;
`terrain` and `terrain_collision` (flat colours by parcel kind; collision is every second grid
vertex); `roads`; `parcel_<ID>_props` (that parcel's fences and trees, visual) and
`parcel_<ID>_props_collision` (its fences, only when the `fences.collision` rule is on), placed in
the parcel's own chunk file so one parcel's props can be swapped at runtime; `props` and
`props_collision` remain only for items without a parcel (OSM trees). The manifest says
`"props_layout": "per_parcel"`; `map_version` went from `0.1.0` to `0.2.0` for this node-layout
change (pre-1.0, a node-layout change bumps the minor part). Also
`parcels.json` (ID, cadastral reference, kind, polygon and anchor in local metres with x east and
y north, chunk, building IDs), `roads.json`, `spawns.json` and `manifest.json` (map version
`0.2.0-slice`, chunk list with triangle counts per node, generated parts, terrain grid info,
attribution, input hashes including the work files). The output has no timestamp and is
byte-identical for identical input.

`make preview` renders `out/preview/topdown.png` (parcels by kind, buildings in wall colour),
`iso.png` (isometric view from the mesh data: terrain relief, roads, buildings, fences, trees;
`make preview EXAG=5` changes the relief exaggeration, default 3) and `iso_close.png` (the same,
zoomed on the densest cluster of buildings), all with a scale bar.

## Viewer

`godot/viewer` loads the whole map at startup with the shared `godot/MapLoader` library
(namespace `Suchohrad.MapLoader`) and lets you walk around in first person.

Map folder: `--map <dir>` after Godot's own args, else the env var `SUCHOHRAD_MAP`, else
`../../out/map` relative to `godot/viewer`. With make: `make viewer MAP=/path/to/out/map`.

- Controls: WASD, mouse look, Space jump, Shift sprint, Escape frees or recaptures the mouse,
  R replaces the nearest parcel with a magenta test cube (`test_cube.tscn`) and restores it on the
  next press.
- Spawn: a random candidate from `spawns.json`; `--seed N` makes it repeatable.
- `make viewer-smoke` (headless; exit code 0 on success): prints chunk, parcel, collider and spawn
  counts, drops the character at 3 spawn points and checks it lands and stays on the ground, then
  tests `ReplaceParcel` / `RestoreParcel`.
- `make viewer-shot` (needs a display): renders `overview`, `oblique`, `street` and `player` views
  at 1600x900 into `out/screens/`; options `--screenshot <path> --view <name> --frames <n>`.

Loader API (`MapLoader`): `Load(dir)`, `Root`, `Parcels` (id, kind, cadastral ref, chunk, building
ids, anchor), `SpawnPoints`, `Stats`, `GroundHeight(x, z)`, `ReplaceParcel(id, PackedScene)`
(hides the parcel's `_visual` node, disables its collision, instantiates the scene at the anchor on
the terrain), `RestoreParcel(id)`. Collision meshes (`*_collision`) become hidden static trimesh
colliders. To guarantee the flat colour look the loader
replaces every visual material with a rough, non-metallic one that uses COLOR_0 (sRGB) as albedo.

### Objects, parcel swap and hot reload

The map folder (map version 0.4.0: `parcels.json` also carries `origin_epsg5514`, the local frame's origin in S-JTSK metres, and the manifest `edit_defaults`, the rule values the editor shows as defaults) also holds `objects.json` (the placed objects planned by the props
stage from `pipeline/config/edits.json`; `files.objects` in `manifest.json`) and `prims/<name>.glb`, one
flat-colour GLB per `prim:` primitive (`prims` in the manifest; same axes as the chunk files, standing on
y = 0). The loader instances every object: `pack:<pack>/<model>` from `assets/manifest.json` (`file`,
resolved against the assets directory), `prim:<name>` from `<map>/prims`. Each object is a node
`Objects/objects_<parcel>/object_<id>` with position (x east, z = -north, y = `z` or the terrain height
under it when `z` is null), `rotation_deg` counter-clockwise seen from above, uniform `scale` and an optional
`colour` (material override). Unknown or missing assets give a warning and a magenta placeholder box.
Objects have no collision in v1.

Assets directory: `--assets DIR`, else env `SUCHOHRAD_ASSETS`, else `<repo>/assets`.

Loader API additions: `ApplyFragment(path)` takes a `parcel-run --out ... --glb ...` fragment, hides the baked
`parcel_<ID>_props` visual and collider of every parcel in `replaces`, drops that parcel's previous dynamic
nodes (`dyn_props_<ID>`) and objects, adds the fragment's props nodes with colliders and its objects. It is
idempotent and an empty result removes the parcel's props. `RevertParcel(id)` restores the baked nodes and
objects. `AssetsDir`, `ObjectNodes`, `DynamicProps`, `Warnings` are exposed.

Hot reload: `make viewer` with `--watch` (`godot --path godot/viewer -- --watch`; off by default, so normal
viewing and headless servers are unaffected):

- `--edits PATH` the edits file (default `pipeline/config/edits.json`), `--area slice|village` (default: from
  the map version), `--state PATH` (default `out/editor-state.json`), env `SUCHOHRAD_UV` (the `uv` executable).
- The file is polled twice a second. The state at startup is assumed to be what the map was built with.
  A change is diffed per parcel and per group (a group change affects all its members and the other way
  round), and only those parcels are regenerated with
  `uv run python -m suchohrad_pipeline parcel-run --area A --parcel ... --edits <snapshot> --glb ... --out ...`
  in the `pipeline` directory (0.3 to 0.9 s) in a subprocess; edits that arrive during a run are coalesced into
  the next one. The viewer prints `edits applied: <ids> in <ms> ms`. A half-written or invalid file is ignored
  until it changes again, a failed `parcel-run` only prints its error. Writers must replace the file atomically
  (temp file, then rename).
- `editor-state.json` (written at most once a second while watching, an ignored build output):
  `{"camera": {"x": east, "y": north, "z": elevation, "yaw_deg": view direction counter-clockwise from east},
  "format_version": 1, "selected": []}`; x and y are in the map frame (local metres). `selected` is the list of
  selected parcel IDs while the editor mode is on (empty otherwise).
- `make viewer-edit-smoke` exports a fresh slice map and a work-directory copy into a scratch directory
  (`SMOKE_DIR=...`, default a temp dir), starts the viewer headless with `--watch`, writes edits files during the
  run and checks objects, swapped props, colliders, replacement without leaks and survival of a broken file.
  `parcel-run`/`export` take `--work DIR` and `export` takes `--out DIR` for such experiments.

## Editor mode

The first visible part of the world map editor: `--editor` starts the viewer in editor mode (it implies
`--watch`); F2 toggles between walk mode (unchanged) and editor mode. Needs `uv` for the hot reload.

```sh
# slice, against the default edits file (pipeline/config/edits.json)
dotnet build godot/viewer/viewer.csproj
godot --path godot/viewer -- --editor --map out/map --area slice
# village
godot --path godot/viewer -- --editor --map out/village/map --area village
```

Options: `--edits PATH` (default `pipeline/config/edits.json`), `--state PATH` (default `out/editor-state.json`),
`--area slice|village`, plus the usual `--map`, `--seed`, `--assets`.

| Key | Action |
| --- | --- |
| F2 | toggle walk / editor mode; walk mode puts the player back where it was |
| W A S D, Q / E | fly, down / up; Shift is 3x faster |
| right mouse (hold) | look around (the mouse is only captured while held) |
| mouse wheel | change the fly speed (shown in the top-left HUD) |
| left click | select the parcel under the cursor; click on nothing clears |
| Shift + left click | add or remove that parcel in the selection |
| G | create a property group (`G-NNNN`) from 2+ selected parcels |
| T | snap to a top-down view above the cursor; again restores the previous camera |
| Esc | clear the selection |

Hovering shows `P-0415 garden` (and `[G-0007]` when grouped) at the cursor. Outlines are unshaded ribbons draped
0.25 m over the terrain: yellow for the selection, orange for property groups (edges shared by two members are
not drawn, so a group reads as one shape), faint white for the hovered parcel. The right-hand panel shows the
selection (ID, kind, area, cadastral reference, group) and the buttons Group selected, Add selected to group,
Remove from group and Dissolve group; Fence, Trees and Objects are placeholders for Editor 6 and 7. The bottom
line shows messages (`saved`, `regenerating P-0004...`, `applied in 480 ms`, errors) and the key hints.

Group operations rewrite `edits.json` atomically (temp file, then rename). The file is reloaded from disk
right before every save, so a change by another writer (e.g. the MCP server) is kept, and everything not
related to groups (fences, trees, objects, unknown parcels) is written back unchanged. The text is exactly what
`suchohrad_pipeline.edits.dump_edits` writes (sorted keys, indent 1, Python float formatting, trailing
newline), so both writers give byte-identical files; `pipeline/tests/fixtures/edits_roundtrip.json` is the fixture
for that. A parcel is in at most one group; `G` refuses (status line) when a selected parcel is already in one.
The watcher then regenerates the affected parcels (the fence runs along a group's outer edge) by itself.

Classes: `EditorMode` (camera, picking, selection, outlines, UI, group operations), `EditsFile` (reader,
canonical writer and group operations for edits.json), `ParcelInfo` (now with `Rings`, `Bounds`, `AreaM2`, `Group`
and `Contains`) and `ParcelIndex` / `MapLoader.ParcelAt(x, z)` (grid index over the parcel boxes; about 5 us per
lookup).

`make viewer-editor-smoke` (`SMOKE_DIR=...` for the scratch directory) exports a slice map into a scratch dir,
starts the viewer headless with `--editor-smoke` and drives the editor through its API: F2 round trip, top-down
snap, picking, selection, outlines (shared edges not drawn), creating and dissolving a group, saved file content
checked byte for byte against `dump_edits`, `editor-state.json`. Screenshots of the editor mode (windowed, needs a
GPU): `godot --path godot/viewer -- --map DIR --edits FILE --state FILE --editor-shot out.png --select P-0003
--shot-at P-0003 [--hover P-0005]`.

## Netcode spike

`godot/netspike` is the gate for the shooter PoC: a headless Godot dedicated server (ENet, 30 Hz,
`CharacterBody3D` players on the real map collision) with up to 64 headless bot clients, one
process each. It compares two replication approaches and probes the `MultiplayerSynchronizer`
64-watched-property issue (godotengine/godot#103938). Results and the recommendation are in
`docs/spikes/netcode-spike.md`.

```sh
export SUCHOHRAD_MAP=/path/to/out/map     # or pass MAP=... to make
make netspike-quick     # N=8, 15 s per variant, short property probe
make netspike           # N=16,32,64, 60 s per variant (builtin, custom, each with and without interest), property probe
python3 godot/netspike/run_spike.py --ns 16 --seconds 20 --variants custom --skip-probe   # custom runs
```

Needs `python3` (stdlib only), `dotnet`, `godot` on `PATH`; `taskset` is used if present to pin the
server and the clients to separate cores. Output (per-run JSON, client sample files, logs,
`summary.json`) goes to `out/netspike/<timestamp>/`. The processes take `--role server|client|
probe-server|probe-client`, `--mode builtin|custom`, `--interest R`; see `Spike.cs`.
